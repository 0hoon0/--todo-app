# 기능 개발 전 설계 문서 먼저 쓰기

이 스킬은 "새 기능을 만들어줘"처럼 기존에 없던 기능을 개발해달라는 요청을 받았을 때 사용합니다. 오타 수정이나 아주 작은 변경에는 사용하지 않습니다.

## 하는 일 (쉬운 말로)

새 기능을 코드로 만들기 전에, "이 기능을 어떻게 만들 건지" 설명하는 문서를 먼저 글로 써서 `.md` 파일로 저장합니다. 집을 짓기 전에 설계도를 먼저 그리는 것과 같습니다. 설계도 없이 바로 집을 지으면 나중에 다시 뜯어고쳐야 할 일이 많아지기 때문입니다.

## 절차

1. **설계 문서 작성**: 아래 "문서 형식"에 맞춰 설계 문서를 작성한다.
2. **저장 위치**: `docs/design/<기능-이름-영문-kebab-case>.md` (예: `docs/design/todo-search.md`). `docs/design/` 폴더가 없으면 새로 만든다.
3. **파일로 저장**: 반드시 실제 `.md` 파일로 저장한다. 대화창에만 설명하고 끝내지 않는다.
4. **구현은 그다음**: 설계 문서를 저장한 뒤에 실제 코드를 작성한다. 설계 내용과 실제 구현이 달라지면, 왜 달라졌는지 설계 문서에 짧게 덧붙여 최신 상태로 맞춘다.
5. 사용자가 명확히 "확인 없이 바로 진행해"라고 말하지 않았다면, 설계 문서를 다 쓴 뒤 사용자에게 "이대로 진행할까요?"라고 한 번 확인받고 나서 구현을 시작한다.

## 문서 형식

```markdown
# <기능 이름>

## 왜 만드나요? (배경)
이 기능이 왜 필요한지, 누가 어떤 문제를 겪고 있는지 한두 문장으로.

## 무엇을 만드나요? (요구사항)
- 이 기능이 꼭 해야 하는 것들을 목록으로.
- 이번에는 하지 않는 것(범위 밖)도 적어둔다.

## 어떻게 만드나요? (설계)
- 어떤 파일을 새로 만들거나 고칠지.
- 데이터(상태)는 어디서 관리하고 어떻게 저장/전달되는지.
- 기존 코드 중 재사용할 함수/컴포넌트가 있다면 명시.

## 예외 상황
입력이 비어있을 때, 네트워크가 끊겼을 때처럼 평소와 다른 상황에서 어떻게 동작해야 하는지.

## 확인 방법
기능이 잘 만들어졌는지 어떻게 테스트/확인할 것인지.
```

문서는 길게 쓸 필요 없습니다. 위 항목이 한 문단씩만 있어도 충분합니다. 핵심은 "코드부터 짜지 않고, 먼저 계획을 글로 남긴다"는 것입니다.
